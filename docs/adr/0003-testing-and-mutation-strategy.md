# ADR 0003: Багаторівнева стратегія тестування (Unit, Integration, E2E) та мутаційний аудит

## Контекст і проблема

Високий показник покриття рядків коду (Line Coverage) та «зелені» тести не гарантують виявлення реальних дефектів бізнес-логіки. Наприклад, тест може викликати ендпоінт скасування запису `PATCH /api/appointments/:id/cancel`, перевірити код `200 OK` і позначити усі рядки сервісу як «покриті», але не помітити, що слот у таблиці `schedules` залишився заблокованим (`isBooked: true`) або що повторне скасування чужого перезаброньованого слоту скидає його статус.

Потрібно обрати стек тестування та архітектуру запуску, які:

1. Дозволяють тестувати ізольовану логіку без БД (Unit), інтеграцію з реальною PostgreSQL (Integration) та повний HTTP-цикл клієнта (E2E).
2. Дають кількісну оцінку здатності тестів ловити баги через мутаційне тестування (`make mutation`).
3. Виключають стан гонитви (race conditions) між тестами при роботі зі спільною базою даних у Docker.

## Розглянуті альтернативи

### 1. Мокування бази даних (In-Memory Mocks / SQLite) проти реальної PostgreSQL в інтеграційних тестах

- **Альтернатива А (Моки Drizzle ORM):** Висока швидкість виконання, але неможливо перевірити реальну роботу SQL-транзакцій, песимістичного блокування `SELECT ... FOR UPDATE`, обмежень `UNIQUE` для `idempotency_key` та `INNER JOIN`.
- **Альтернатива Б (Реальна PostgreSQL у Docker + очищення `TRUNCATE ... RESTART IDENTITY CASCADE`):** Повна відповідність production-середовищу.
- **Рішення:** Обрано **Альтернативу Б** для інтеграційних та E2E-тестів, а моки (`vi.fn()`, `vi.spyOn()`) залишено виключно для Unit-тестів модуля `resilience.ts` та гілок `error-handler.ts`.

### 2. Спосіб ізоляції HTTP-сервера для Integration та E2E

- Виділено фабрику `buildApp()` у `src/app.ts` окремо від точки входу `src/index.ts`.
- Для **Integration-тестів** використано `app.inject()` (in-memory HTTP-маршрутизація Fastify разом із реальною PostgreSQL).
- Для **E2E-тестів** використано підняття реального TCP-сокета на динамічному вільному порту `app.listen({ port: 0, host: '127.0.0.1' })` та зовнішні мережеві запити через стандартний `fetch()`.

### 3. Інструмент мутаційного тестування та паралелізм

- Обрано **Stryker Mutator** (`@stryker-mutator/core` + `@stryker-mutator/vitest-runner`) з аналізом покриття `perTest`.
- Оскільки інтеграційні та E2E-тести модифікують реальну БД, у `vitest.config.ts` (`fileParallelism: false`) та `stryker.config.json` (`concurrency: 1`) встановлено послідовне виконання воркерів. Це гарантує 100% детермінованість мутаційного прогону без взаємного затирання даних між мутантами.

## Наслідки

- **Позитивні:**
  - Мутаційний аналіз виявив 27 реальних прогалин у першому («зеленому») наборі тестів.
  - Після підсилення асертів досягнуто **100% Mutation Score** у `src/services/appointments.service.ts` (45/45) та `src/db/resilience.ts` (21/21), а загальний показник склав **93.88%**.
  - Весь цикл перевірки відтворюється однією командою `make mutation` (або `npm run mutation`).
- **Негативні / Компроміси:**
  - Через роботу зі справжньою PostgreSQL та `concurrency: 1` повний прогін 98 мутантів займає близько 3 хвилин 15 секунд, що є прийнятним компромісом заради достовірності транзакційних тестів.
