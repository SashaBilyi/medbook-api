# ADR 004: Організація CI/CD, блокування злиття та міграцій без простою

## Контекст і проблема

При розробці та експлуатації веб-сервісу виникають три критичні ризики:

1. Потрапляння невідформатованого, синтаксично некоректного або неробочого коду в основну гілку `main` через людський фактор.
2. Простій сервісу (Downtime) під час деплою, якщо нова версія застосунку починає приймати трафік до повної ініціалізації або якщо стара версія вбивається миттєво.
3. Блокування таблиць бази даних (`ACCESS EXCLUSIVE LOCK`) під час виконання DDL-міграцій та створення індексів, а також падіння інстансів за таймаутом Readiness Check, якщо міграції запускаються безпосередньо в команді старту сервера (`npm start`).

---

## Розглянуті варіанти

### Варіант 1: Запуск міграцій при старті застосунку + Auto-Deploy з Git

- **Опис:** Render автоматично деплоїть кожен коміт у `main`, а команда старту має вигляд `npm run db:migrate && node dist/index.js`.
- **Недоліки:**
  - Якщо міграція або створення індексу триває довше за таймаут Health Check, платформа вбиває контейнер і перезапускає його в нескінченному циклі.
  - При масштабуванні (кілька інстансів) виникає стан гонитви (race condition) між контейнерами, що одночасно намагаються змінити схему БД.
  - Неможливо виконати `CREATE INDEX CONCURRENTLY` всередині стандартної транзакційної міграції ORM.

### Варіант 2: Розділення CI та CD у GitHub Actions, ізольовані 3-фазні міграції та Blue-Green через Deploy Hook (Обрано)

- **Опис:**
  - GitHub Actions відповідає за перевірку PR (`ci.yml`) та оркестрацію релізу (`cd.yml`).
  - GitHub Rulesets технічно блокує кнопку Merge при падінні будь-якої перевірки.
  - Міграції винесені з `npm start` у CD-пайплайн і розділені на `schema` (із `lock_timeout`), `data` (батчі) та `indexes` (`CONCURRENTLY`).
  - Render деплоїть новий код лише за командою Deploy Hook після завершення всіх міграцій і перемикає трафік за сигналом `/api/health`.

---

## Прийняті рішення

1. **CI та Merge Blocking:** Використовувати GitHub Actions (`ci.yml`) у зв'язці з GitHub Branch Rulesets. Обов'язковий статус-чек `Lint, Build, Migrate & Test` перевіряє Conventional Commits, Prettier, ESLint, збірку TypeScript та проганяє всі міграції й тести на сервісному контейнері PostgreSQL 16.
2. **Архітектура Zero-Downtime міграцій:**
   - Розділити міграції на 3 окремі CLI-скрипти: `db:migrate:schema`, `db:migrate:data`, `db:migrate:indexes`.
   - Заборонити виконання `db:seed` у staging/production конвеєрах.
   - Створювати індекси виключно через `CREATE INDEX CONCURRENTLY IF NOT EXISTS` поза транзакцією.
3. **Платформа Stage та Blue-Green Deployment:**
   - Використовувати Render (Web Service + Managed PostgreSQL у регіоні Frankfurt).
   - Вимкнути автоматичний деплой на Render (`Auto-Deploy: No`) та передавати керування GitHub Actions через секрет `RENDER_DEPLOY_HOOK_URL`.
   - Налаштувати `Health Check Path: /api/health` для реалізації Blue-Green перемикання без втрати з'єднань.
   - Додати ендпоінт `/api/version`, який повертає поточний `commitSha` для прозорої верифікації релізу.
4. **Безпека та конфігурація CI/CD:**
   - Зовнішні підключення з GitHub Actions до БД Render виконувати з обов'язковим шифруванням (`?sslmode=require`), тоді як веб-сервіс всередині мережі Render використовує Internal Database URL.
   - Перевірку наявності секретів у кроках `if:` GitHub Actions виконувати через проміжні змінні оточення (`env`) на рівні `job`, дотримуючись обмежень безпеки GitHub.

## Наслідки

### Позитивні:

- **Нульовий простій (Zero-Downtime):** Користувачі не отримують помилок `502`/`503` під час оновлення коду чи побудови індексів у БД.
- **Гарантована якість у `main`:** Жоден коміт із помилками лінтера, типів або зламаними міграціями не може бути влитий у головну гілку.
- **Швидкий старт інстансів:** Веб-сервер стартує за частки секунди, не чекаючи на завершення операцій у базі даних.
- **Прозорість релізів:** За допомогою `/api/version` у будь-який момент можна перевірити, який саме коміт наразі обслуговує трафік.

### Компроміси та обмеження:

- Видалення застарілих колонок або таблиць (фаза Contract) не може виконуватися в одному релізі зі зміною коду й потребує окремого наступного PR після того, як старий код повністю вийде з експлуатації.
