# ADR 0002: Організація роботи з БД, транзакцій та ідемпотентності

**Контекст:**
При переході зі статичних даних на реальну реляційну БД (PostgreSQL) виникають ризики: подвійне бронювання одного слоту (race condition), дублювання записів при мережевих збоях клієнта, тимчасова недоступність БД та деградація продуктивності через проблему N+1.

**Розглянуті альтернативи:**

- _Захист від подвійного запису:_ Перевірка в коді додатку (небезпечно при паралельних запитах) vs Транзакції БД з блокуванням / атомарним оновленням.
- _Ідемпотентність:_ Зберігання ключів у Redis vs Унікальний індекс `idempotency_key` безпосередньо в таблиці `appointments` PostgreSQL.

**Рішення:**

1. **Транзакційність:** Використовувати `db.transaction()` у Drizzle ORM для атомарного оновлення статусу слоту (`schedules.is_booked`) та створення запису в `appointments`.
2. **Ідемпотентність на рівні БД:** Додати поле `idempotency_key` з обмеженням `UNIQUE` у таблицю `appointments`. Це гарантує ідемпотентність без залучення зовнішнього кешу (Redis).
3. **Запобігання N+1:** Заборонити довантаження даних лікаря в циклі; використовувати виключно реляційний `innerJoin` у Drizzle.
4. **Обробка збоїв БД:** Реалізувати утиліту `withRetry` (до 3 спроб із затримкою) для перехоплення тимчасових мережевих збоїв БД і повернення коректного HTTP `503`, якщо БД недоступна.

**Наслідки:**

- Система стійка до повторних відправок форми (double-click) та короткочасних розривів з'єднання з БД.
- Схема БД містить технічне поле `idempotency_key`.
