## 2. Аудит: Топ-3 місця, де «зелені» тести не ловили реальні баги (та як їх підсилено)

Під час першого прогону Stryker на 100% «зелених» базових тестах вижило **32 мутанти з 98** (Mutation Score: **66.33%**). Аналіз виявив 3 критичні прогалини:

1. **Прогалина №1: Скасування запису не звільняло слот + вразливість повторного скасування (`src/services/appointments.service.ts:85` та `:73`)**
   - _Який баг пропустили зелені тести:_ Мутант замінив `.set({ isBooked: false })` на `.set({ isBooked: true })`, а також видалив ранній вихід `if (appointment.status === 'cancelled') return appointment;`. Базовий тест перевіряв лише `statusCode === 200` та `status === 'cancelled'` у відповіді, не перевіряючи стан таблиці `schedules`. Якби баг потрапив у продакшн: (а) скасовані слоти назавжди залишалися б недоступними для запису; (б) якби Пацієнт 1 скасував запис, Пацієнт 2 забронював цей слот, а Пацієнт 1 повторно викликав `PATCH /cancel` для свого старого запису — система б скинула `isBooked: false` на активному записі Пацієнта 2.
   - _Як підсилено:_ У `api.integration.test.ts` та `booking-flow.e2e.test.ts` додано кроки повторного бронювання слоту `102`/`103` іншим пацієнтом після скасування, а після повторного виклику `PATCH /cancel` на старому записі — перевірку `expect(slot102.isBooked).toBe(true)`. Усі мутанти в `appointments.service.ts` знищені (**45/45 Killed — 100%**).

2. **Прогалина №2: Відключення Exponential Backoff та зайва затримка після останньої спроби (`src/db/resilience.ts:28-29`)**
   - _Який баг пропустили зелені тести:_ Мутанти видалили тіло блоку `if (attempt < retries) {}`, замінили множення на ділення `delayMs / Math.pow(2, attempt - 1)` та змінили умову `attempt < retries` на `attempt <= retries`. Базовий unit-тест перевіряв лише `expect(operation).toHaveBeenCalledTimes(3)`, не контролюючи реальні таймінги очікування.
   - _Як підсилено:_ У `tests/unit/resilience.test.ts` додано шпигуна `vi.spyOn(globalThis, 'setTimeout')`, який записує точні значення затримок у масив `recordedDelays`. Додано перевірку `expect(recordedDelays).toEqual([200, 400])` (рівно 2 паузи для 3 спроб із множником $\times 2$) та `expect(timeoutSpy).not.toHaveBeenCalled()` при миттєвому успіху чи `BusinessError`. Усі мутанти в `resilience.ts` знищені (**21/21 Killed — 100%**).

3. **Прогалина №3: Втрата структури та текстів помилок у HTTP-відповідях (`src/api/error-handler.ts:13, 21, 28` та `appointments.service.ts:36, 40, 70`)**
   - _Який баг пропустили зелені тести:_ Мутанти замінили об'єкти відповідей на порожні `reply.code(...).send({})` та очистили повідомлення `new BusinessError(404, "")`. Тести перевіряли лише `res.statusCode`, тому клієнт отримував би порожній JSON `{}` замість причин помилки.
   - _Як підсилено:_ У всіх трьох рівнях тестів додано перевірку тіла помилок через `expect(res.json()).toEqual({ error: '...', message: '...' })`.

### Класифікація решти 6 невбитих мутантів (усі у `src/api/error-handler.ts`)

1. **Реальні прогалини (Real gaps): 0 шт.** (усі 27 реальних прогалин із базового прогону усунено).
2. **Еквівалентні мутанти (Equivalent): 5 шт.**
   - `src/api/error-handler.ts:19` (4 мутанти `ConditionalExpression` / `LogicalOperator` у виразі `if (typeof error === 'object' && error !== null && 'validation' in error)`): у середовищі Fastify в `setErrorHandler` параметр `error` під час виконання **завжди** є об'єктом класу `Error` (не `null` і не примітив). Перевірки `typeof error === 'object'` та `error !== null` вимагаються виключно компілятором TypeScript (`strict: true`), щоб дозволити застосування оператора `'validation' in error` до типу `unknown`. Заміна цих умов на `true` не змінює поведінку рантайму.
   - `src/api/error-handler.ts:20` (1 мутант `[NoCoverage] StringLiteral` у `error instanceof Error ? error.message : 'Validation error'`): Fastify Ajv завжди створює помилки валідації як екземпляри `Error`, тому друга гілка тернарного оператора є захисним фолбеком для тайпгарду TypeScript і не може виконатися в рантаймі.
3. **Прийнятні мутанти (Acceptable): 1 шт.**
   - `src/api/error-handler.ts:27` (`CallExpression`: видалення виклику `request.log.error(error)` перед поверненням `503 Service Unavailable`): виклик логера є побічним інфраструктурним ефектом і не змінює HTTP-відповідь клієнту. Мокування внутрішнього Pino-логера Fastify прив'язало б тести до деталей реалізації фреймворку.
