# DEFENSE — Завдання 2: Реалізація сценаріїв та інтеграція з БД

**Що я реалізував (1–2 речення):**
Спочатку реалізував базові сценарії розкладу та запису до лікаря (`GET /schedules`, `POST /appointments`, `PATCH /appointments/:id/cancel`) на статичних `in-memory` даних, після чого перевів систему на PostgreSQL + Drizzle ORM. Забезпечив транзакційність із песимістичним блокуванням (`SELECT ... FOR UPDATE`), ідемпотентність через `Idempotency-Key`, вибірку без проблеми `N+1` (`INNER JOIN`) та обробку збоїв БД із механізмом повторних спроб (`withRetry` з exponential backoff).

**Топ-3, де я «зрізав кути» / знайшов і виправив (проти spec):**

1. **Загроза N+1 при переході зі статики на БД:** У статичному прототипі отримання імені лікаря для кожного слоту виконувалося в циклі (`.map()` + `.find()`). Пряме перенесення цієї логіки на БД породило б класичну проблему `N+1` (1 запит на розклад + N запитів на лікарів). Я замінив це на єдиний реляційний запит із `innerJoin(doctors, eq(schedules.doctorId, doctors.id))`.
2. **Падіння `db:seed` через мультикомандний SQL у prepared statement:** ШІ згенерував у `src/db/seed.ts` один виклик `db.execute(sql\`...\`)`, який містив одразу три команди `CREATE TABLE`. Драйвер `postgres-js`за замовчуванням використовує розширений протокол PostgreSQL, який забороняє кілька команд в одному prepared statement. Я розділив ініціалізацію таблиць на окремі виклики`db.execute`і додав вивід`err.cause` для діагностики помилок драйвера.
3. **Конфлікт порту `5432` із локальною службою PostgreSQL у Windows:** При запуску `db:seed` підключення до `localhost:5432` перехоплювалося фоновою службою PostgreSQL самої ОС Windows замість Docker-контейнера, що викликало помилку автентифікації пароля. Я виявив причину через аналіз `err.cause` та переніс зовнішній порт контейнера в `docker-compose.yml` та `src/db/index.ts` на ізольований порт `5433`.

**Ключове рішення - які альтернативи зважив і чому обрав цю (ADR):**
Для захисту від подвійного бронювання (race conditions) та дублювання запитів при мережевих збоях я зважив перевірку на рівні коду додатку та окремий кеш у Redis проти засобів самої PostgreSQL. Обрав комбінацію **транзакцій Drizzle (`db.transaction`) із блокуванням рядка `SELECT ... FOR UPDATE`** та **унікального індексу `idempotency_key` у таблиці `appointments`**. Це гарантує атомарність і сувору ідемпотентність без ускладнення інфраструктури додатковим Redis-сервером. Також у `withRetry` відокремив бізнес-помилки (`BusinessError`: `404`, `409`), які повертаються клієнту миттєво, від інфраструктурних збоїв БД, які повторюються 3 рази перед поверненням `503 Service Unavailable`. Деталі у `docs/adr/0002-db-transactions-and-resilience.md`.

**Перевірка (на реально запущеній системі):**

- `npm run db:seed` → `Database initialized and seeded successfully.`
- `GET /schedules` → `200 OK` (повертає слоти з даними лікарів одним `INNER JOIN` запитом).
- `POST /appointments` (з `Idempotency-Key: db-key-1`) → `201 Created`; повторний запит із тим самим ключем → `200 OK` (повертає створений запис без дублювання).
- Конкурентний `POST /appointments` на зайнятий слот (з іншим ключем) → `409 Conflict`.
- `PATCH /appointments/1/cancel` → `200 OK` (транзакційно змінює статус на `cancelled` і звільняє слот у `schedules`).
- Відмова БД (`docker compose stop postgres` + запит `GET /schedules`) → після 3 ретраїв контрольовано повертає `503 Service Unavailable` без падіння процесу сервера; після `docker compose start postgres` автоматично відновлює роботу.
- `npm run test:smoke` та `npm run lint` → проходять без помилок.
