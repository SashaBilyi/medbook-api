# DEFENSE — Лабораторна робота №4

## Короткий опис реалізованого рішення

У межах лабораторної роботи налаштовано цикл CI/CD у GitHub Actions, політику блокування неперевірених Pull Request через GitHub Rulesets, трифазні міграції бази даних без простою (Zero-Downtime Migrations) та Blue-Green розгортання на публічний хмарний майданчик **Render** (Web Service + Managed PostgreSQL).

## 1. Докази роботи CI та блокування мерджу (Аудит)

- **Основний Pull Request:** https://github.com/SashaBilyi/medbook-api/pull/4
- **Налаштування захисту гілки (`main`):**
  - Увімкнено GitHub Ruleset у статусі `Active` для гілки `main`.
  - Активовано опції `Require a pull request before merging`, `Require status checks to pass` (обов'язкова перевірка: `Lint, Build, Migrate & Test`) та `Require branches to be up to date before merging`.

### Хід аудиту (падіння CI -> блокування -> виправлення -> дозвіл на мердж):

1. **Спрацювання захисту CI (Червоний прогін):**
   - Під час початкових прогонів конвеєр `CI Quality Gate` виявив порушення правил лінтера (`no-console` у скриптах міграцій) та некоректний формат повідомлення merge-коміту. Злиття Pull Request було автоматично заблоковано правилом Ruleset.
2. **Виправлення та розблокування (Зелений прогін):**
   - Унесено виправлення в конфігурацію та скрипти (`fix(db): disable no-console rule for migration scripts`, оновлено регулярний вираз для merge-комітів у `ci.yml` та синтаксис змінних оточення у `cd.yml`).
   - Повторний прогін пройшов лінтинг, збірку, усі 3 фази міграцій на тимчасовому сервісному контейнері PostgreSQL 16 та тести, після чого кнопка `Merge pull request` розблокувалася.

## 2. Робота CD та публічного стейджу (Render)

- **Публічний URL перевірки версії (`/api/version`):** https://medbook-api-stage.onrender.com/api/version

### Як вирішено інфраструктурні проблеми під час налаштування CD:

- **SSL/TLS для зовнішніх міграцій:** Під час першого запуску CD підключення з ранера GitHub Actions до бази Render впало з помилкою `PostgresError: SSL/TLS required`. Проблему вирішено додаванням параметра `?sslmode=require` до секрету `STAGING_DATABASE_URL`, що забезпечило шифрований канал для виконання міграцій.
- **Безпечна робота з `secrets` у GitHub Actions:** Пряме звернення до контексту `secrets` в умовах `if:` замінено на мапінг через змінні оточення на рівні `job` (`env.STAGING_DB_URL`, `env.HOOK_URL`, `env.APP_URL`), щоб задовольнити вимоги безпеки парсера GitHub Actions.

## 3. Архітектура міграцій без простою та Blue-Green Deployment

1. **Відокремлення міграцій від запуску сервера:**
   - Команда старту на Render (`npm start`) запускає виключно скомпільований сервер (`node dist/index.js`). Це гарантує миттєвий старт контейнера та стабільне проходження Readiness Check, усуваючи ризик перезапусків (CrashLoopBackOff) через таймаути тривалих міграцій.
2. **Трифазний конвеєр міграцій у CD:**
   - `npm run db:migrate:schema` — виконує структурні зміни (Expand-фаза) із захисним `SET LOCAL lock_timeout = '5s'`, щоб не блокувати активні запити до бази даних від користувачів.
   - `npm run db:migrate:data` — виконує неблокуюче оновлення даних невеликими батчами. Скрипт тестових даних (`db:seed`) повністю виключено з CD-конвеєра.
   - `npm run db:migrate:indexes` — створює індекси окремим кроком поза транзакційним блоком за допомогою директиви `CREATE INDEX CONCURRENTLY IF NOT EXISTS`.
3. **Blue-Green перемикання трафіку:**
   - Автоматичний деплой з Git на Render повністю вимкнено. Деплой ініціюється виключно через **Deploy Hook** після успішного завершення всіх трьох кроків міграцій БД у воркфлоу `cd.yml`.
   - Завдяки налаштованому `Health Check Path: /api/health`, Render тримає старий інстанс активним, піднімає нову версію паралельно і перемикає балансувальник трафіку на новий реліз лише після отримання коду `200 OK`.
