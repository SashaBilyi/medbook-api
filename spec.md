# Специфікація продуктивності, навантаження та модульної архітектури (Лабораторна робота №5)

## 1. Мета та контекст

Знайти реальні вузькі місця (bottlenecks) сервісу **MedBook API** за даними з реально запущеної системи (Node.js + Fastify + PostgreSQL 16 + HTML UI), локалізувати та захистити найкритичніші проблеми продуктивності, а також винести найвразливіший модуль у відокремлену бібліотеку з чистим **Dependency Injection (DI)** та строго типізованим публічним контрактом TypeScript.

---

## 2. Реалістичний датасет навантаження (Load Dataset)

Стандартний `db:seed` створює лише 2 лікарі та 3 слоти, що недостатньо для виявлення реальних проблем планувальника PostgreSQL, пам’яті та серіалізації. Для відтворюваних навантажувальних випробувань використовується окремий детермінований скрипт `npm run db:seed:load`:

| Таблиця        | Кількість рядків | Характеристика даних                                                             |
| -------------- | ---------------- | -------------------------------------------------------------------------------- |
| `doctors`      | `100`            | 100 лікарів у 10 спеціалізаціях                                                  |
| `schedules`    | `25 000`         | 250 слотів на кожного лікаря (~60% вільних `is_booked = false`, ~40% зайнятих)   |
| `appointments` | `15 000`         | ~10 000 `confirmed` (прив’язані до зайнятих слотів) + ~5 000 `cancelled` історії |

Після наповнення обов’язково виконується `ANALYZE doctors, schedules, appointments;`, щоб планувальник PostgreSQL працював із реальною статистикою розподілу рядків.

## 3. Сценарії навантаження

Усі сценарії виконуються проти скомпільованого продакшн-сервера (`npm run build` → `node dist/index.js`) та реальної PostgreSQL 16 у Docker.

### Сценарій 1: `read-schedules` — перегляд розкладу лікарів

- **Бізнес-контекст:** пацієнти відкривають сторінку запису й переглядають розклад доступних слотів.
- **Запит:** `GET /api/schedules` (Baseline: без параметрів; After: типові параметри перегляду з пагінацією та фільтром, а також перевірка захисту unbounded-виклику).
- **Параметри:** `10` одночасних з’єднань, тривалість `8s` на повтор.

### Сценарій 2: `read-appointments` — перегляд реєстру записів

- **Бізнес-контекст:** адміністратор/реєстратура завантажує список записів пацієнтів.
- **Запит:** `GET /api/appointments`.
- **Параметри:** `10` одночасних з’єднань, тривалість `8s` на повтор.

### Сценарій 3: `mixed-clinic` — типова змішана робота сервісу

- **Бізнес-контекст:** одночасна робота пацієнтів і реєстратури у звичайному режимі клініки.
- **Розподіл трафіку:**
  - **70% читання:** `GET /api/schedules` (40%), `GET /api/doctors` (15%), `GET /api/appointments` (15%).
  - **20% бронювання:** `POST /api/appointments` (15% нових бронювань вільних слотів + 5% ідемпотентних повторів із наявним `Idempotency-Key`).
  - **10% скасування:** `PATCH /api/appointments/:id/cancel` (скасування наявних записів і звільнення слотів).
- **Параметри:** `12` одночасних з’єднань, тривалість `10s` на повтор.

### Сценарій 4: `booking-contention` — конкурентне бронювання гарячих слотів (Write Contention)

- **Бізнес-контекст:** піковий наплив пацієнтів на популярні слоти одного лікаря + повторні кліки (double-click) з однаковим `Idempotency-Key` одночасно.
- **Запит:** 100% `POST /api/appointments` по обмеженому набору з 20 гарячих слотів (включно з паралельними дублями `Idempotency-Key`).
- **Параметри:** `20` одночасних з’єднань, тривалість `8s` на повтор.
- **Мета:** виявити черги на `SELECT ... FOR UPDATE`, вичерпання пулу з’єднань `max: 10`, поведінку `withRetry` та можливі `503` через race condition на `UNIQUE(idempotency_key)`.

### Сценарій 5: `(Фронт) UI Booking Page` — `GET /ui` (Lighthouse / Web Vitals)

- **Бізнес-контекст:** невелика веб-сторінка запису пацієнтів на прийом (`GET /ui`), що завантажує список лікарів та розклад із REST API та дозволяє бронювати/скасовувати слоти.
- **Перевірка:** аудит через Google Lighthouse (Performance, Accessibility, Best Practices, SEO) + вимірювання Web Vitals (`TTFB`, `FCP`, `LCP`, `TBT`, `CLS`).

## 4. Методика вимірювань, метрики та відтворюваність

1. **Ідентифікація збірки:** перед кожним прогоном раннер запитує `GET /version` і записує `service`, `version`, `commitSha`, версію винесеного модуля та версію Node.js у JSON-звіт.
2. **Повтори та розкид:** кожен сценарій проходить **1 warm-up прогін** (не враховується у статистиці) + **5 незалежних вимірювальних повторів**. Для кожного сценарію обчислюються:
   - Перцентилі затримки: `p50`, `p95`, `p99`, `max` (ms);
   - Пропускна здатність: `RPS` (req/s) та `MB/s`;
   - Розподіл HTTP-статусів (`2xx`, `4xx`, `5xx`, таймаути);
   - Розкид між повторами: `mean`, `min`, `max`, `stddev`, `CV%`.
3. **CPU vs очікування (Wait / I/O):**
   - Профілювання V8 (`node --cpu-prof`) з автоматичним розбором профілю на активний JS/Runtime CPU vs `(idle)`/очікування I/O та `(garbage collector)`;
   - `process.cpuUsage()` (`user + system` відносно wall-clock часу);
   - `performance.eventLoopUtilization()` та `monitorEventLoopDelay()` (`p50`, `p95`, `p99`).
4. **RAM:** періодичний семплінг `process.memoryUsage()` (`rss`, `heapUsed`, `heapTotal`, `external`) до, на піку та після навантаження.
5. **Аналіз БД (PostgreSQL):**
   - `COUNT(*)` та `pg_stat_user_tables` (`n_live_tup`, `seq_scan`, `idx_scan`, розмір таблиць);
   - `pg_indexes` та `pg_stat_user_indexes`;
   - `EXPLAIN (ANALYZE, BUFFERS)` для кожного ключового запиту.
6. **Відтворювані команди:**
   - `make load` (`npm run load`) — повний навантажувальний прогін усіх сценаріїв із повторами та збереженням звіту.
   - `make profile` (`npm run profile`) — CPU/RAM профілювання під навантаженням + повний аналіз БД (`EXPLAIN ANALYZE`, індекси, рядки).
   - `GET /version` (та `/api/version`) — версія сервісу, `commitSha` та версії внутрішніх модулів.

## 5. Критерії прийняття (SLO та архітектурні вимоги)

### Продуктивність (цільові SLO після оптимізації)

- `GET /api/schedules` (перегляд із пагінацією/фільтром): `p95 < 50 ms`, `p99 < 100 ms`, `0` помилок `5xx`.
- `GET /api/appointments`: `p95 < 50 ms`, `p99 < 100 ms`, `0` помилок `5xx`.
- `mixed-clinic`: `p95 < 100 ms`, `p99 < 200 ms`, `0` помилок `5xx`.
- `booking-contention`: `0` помилок `5xx` (коректна обробка конкуренції `409 Conflict` та ідемпотентного replay `200 OK` без помилкових `503` на `23505`).
- RAM: стабільне споживання без неконтрольованого зростання `heapUsed` після завершення навантаження.
- БД: `Index Scan` / `Index Only Scan` для фільтрованих/пагінованих запитів без повного сканування всієї таблиці.
- Фронт (`GET /ui`): Lighthouse Performance `>= 90`, `CLS < 0.1`, `TBT < 100 ms`.

### Архітектура винесеної бібліотеки з DI

- Найвразливіший модуль (визначений виключно за даними профілювання) винесений у локальний workspace-пакет `packages/<module-name>`.
- **Чистий DI:** усі залежності (репозиторій/транзакції БД, політика ретраїв, логер/хуки метрик) передаються через інтерфейси-порти у фабрику/конструктор.
- **Нульова обізнаність про реалізації:** базовий модуль має `"dependencies": {}` і не імпортує `drizzle-orm`, `postgres`, `fastify` чи будь-який код із `src/`.
- **Типізований публічний контракт:** суворий TypeScript (`strict: true`, `declaration: true`), публічні DTO/порти/доменні помилки експортуються через `index.ts` → `dist/index.d.ts`.
- **Верифікація:** бібліотека покрита автономними unit-тестами на in-memory адаптерах (без БД), а `medbook-api` підключає її через PostgreSQL/Drizzle адаптери в Composition Root і проходить усі Integration/E2E тести.
