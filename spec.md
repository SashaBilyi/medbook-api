# Специфікація: MedBook API

## 1. Що і навіщо

MedBook API — це сервіс для автоматизації процесу запису пацієнтів до лікарів. Мета проєкту — створити надійний, типізований бекенд для перегляду розкладу лікарів та бронювання слотів із запобіганням подвійним записам.

## 2. Розбиття на компоненти (Модулі)

- **Users Module (`src/modules/users`):** Керування профілями пацієнтів і лікарів.
- **Schedules Module (`src/modules/schedules`):** Логіка створення та перегляду вільних слотів лікаря.
- **Appointments Module (`src/modules/appointments`):** Ядро бізнес-логіки. Бронювання, скасування та зміна статусу прийому.
- **Database Core (`src/db`):** Підключення до PostgreSQL, схеми таблиць та міграції Drizzle ORM.

## 3. Дані та зв'язки (ER-модель)

- `User` (id, role, name, email)
- `DoctorProfile` (id, user_id, specialization) — зв'язок `1:1` з `User`.
- `Schedule` (id, doctor_id, date, start_time, end_time) — зв'язок `1:N` від `DoctorProfile`.
- `Appointment` (id, patient_id, schedule_id, status) — зв'язує пацієнта (`User`) та слот (`Schedule`).

## 4. Як дані оновлюються за ключовими сценаріями

**Сценарій бронювання прийому:** При спробі записатися система перевіряє відсутність існуючого `Appointment` на вказаний `schedule_id` зі статусом `confirmed`. Для уникнення `race conditions` (подвійного запису) використовуються транзакції БД на рівні Drizzle ORM.

## 5. Критерії прийняття (Acceptance Criteria)

1. Код жорстко розділено за модулями, відсутні циклічні залежності.
2. Налаштовано `git-hook`, який блокує коміт/пуш, якщо код не пройшов `lint` або `smoke-test`.
3. Усі залежності (devDependencies/dependencies) обґрунтовані та використовуються.
4. Наявний файл `DEFENSE.md` та `ADR` щодо ключових архітектурних рішень.
